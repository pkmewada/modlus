# Permission Module – Current Architecture & Implementation Summary

## Objective

Build a scalable, database-driven permission system for the PHP/MySQL admin application that supports:

* Role-based permissions
* Employee-specific overrides
* Centralized route protection
* Future expansion without code changes

The goal is to avoid hardcoded permissions and manage access completely from the database.

---

# 1. Database Structure

## routesMaster

Master table containing all application routes/pages.

Purpose:

* Single source of truth for every page.
* Controls menu visibility, public/private pages, route hierarchy, and modules.

Key Fields:

text
id
routePath
pageFile
routeTitle
moduleName
layoutType
iconClass
parentRouteId
isPublic
isMenuVisible

## rolePermissions

Stores default permissions for a role.

Example:

text

HR
Account Manager

Each role can have:

text

## userPermissionOverrides

Stores employee-specific overrides.

Purpose:

Allow one employee to have permissions different from their role.

Example:

text

Employee Leads = Denied


Stored Fields:

text

# 4. Route Protection

Implemented inside:

text
routes.php


Every page request now passes through centralized permission checking.

Flow:

text
Route Request
      ↓
Find Route in routesMaster
      ↓
Check Public Page?
      ↓
Check User Override?
      ↓
Check Role Permission?
      ↓
Allow / Deny


---

# 5. Permission Resolution Priority

Current priority:

text
1. User Permission Override
2. Role Permission
3. Default Deny


Example:

Role:

text
Web Developer


Permission:

text
Employee Leads = Allowed


Employee Override:

text
Employee Leads = Denied


Final Result:

text
Denied


Because User Override always wins.
